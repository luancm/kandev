**Private seam:** Retain the current Stopper compatibility until its callers migrate, but production cancellation must use an identity-aware capability. The capability methods are `CancelErrandWithTarget(ctx, row, commit func(ErrandTeardownTarget) error) error` and `RetryErrandTeardown(ctx, intent) (TeardownOutcome,error)`, where outcomes are `completed` or `superseded`; unknown is an error. The first method uses existing cancellation ownership/guard mechanics, captures trusted target, calls **only** the durable CAS callback under that guard, then executes/arranges bounded teardown. Publish DTOs, wake awaiters and deliver cancellation notices after releasing guard and DB write. Fakes used for tests must implement the complete capability. Missing identity-aware capability in production is a wiring error, not permission to fall back to broad stop-by-session.

**Capability data contract:** `ErrandTeardownTarget` is the immutable `Target` value persisted by Task 09: `TaskID`, `SessionID`, `SessionIncarnation`, `ExecutionID`, `TurnID`, `NoTurn`, `SubmissionID`, `FirstTurnID`, and `ReservedSubmissionID`, plus `PromptGeneration` for same-process revalidation only. Use the existing canonical incarnation/generation types, not a new identity encoding. Session targets require verified incarnation and a turn or explicit `NoTurn`; reserved targets require both reserved turn and submission and no fabricated execution. `ErrandTeardownIntent` adds `ID`, `Version`, `State`, `RequestedAt` and this target. `TeardownOutcome` is a closed string enum `completed` or `superseded`; the zero value with a non-nil error leaves the exact intent pending. No `nil` error represents scheduled, unknown or retryable work. A read/stop/commit error preserves the intent for the existing sweep. `CancelErrandWithTarget` returns nil only after the captured intent is durably completed/superseded; if cancellation committed but stop failed, it returns the error while keeping logical cancellation committed. The callback captures the cancellation source/reason and may perform only the Task 09 CAS transaction. On retry the adapter accepts the persisted intent, never a freshly resolved session-only stop target.

**Algorithm:**

1. Under existing session cancellation ownership, resolve immutable row role/task/parent/incarnation and the current active-or-latest turn + exact execution. Use `captureCancellationIdentity`/`capturePromptActivity` and stored delivery authority, not caller input. A transient read error before capture returns an error and leaves the errand row unchanged; the next bulk call can retry because it is still live. For a queued row with no session and no admitted launch, capture the reserved launch tuple as an explicit pre-session target.
2. Route a generic user `StopSession` for a positively identified errand once through the same identity-aware cancellation path. Its adapter must use the exact low-level stop, not call `StopSession` recursively. Preserve ordinary-session authorization/cascade behavior; a failed role read never means ordinary permission. Migrate `CancelOnSessionStop` as part of that routing so an observer-only hook cannot leave an untracked async stop. The callback atomically writes logical cancellation, the pending intent and existing result/cancellation-source behavior. Repeated cancel preserves intent ID/target/notice/result delivery metadata. It may retry pending teardown but never creates another notice or increments the logical cancellation count again.
3. Complete/stop only the captured target. Under the same arbitration used for prompt admission, re-read session incarnation and current/last turn and check execution ownership. Do not acquire lifecycle while waiting on a cancel guard in the inverse order; use the coordinator's unlock/relock and existing try-acquire/yield patterns. Never hold SQL over runtime I/O or call a lock-reentrant manager method from a published session transition.
4. If target incarnation still matches, no successor turn/submission has been admitted, and execution matches, make the logical session transition conditional on that evidence, register exact execution stop ownership, and call runtime stop for the **captured execution ID**. Keep cancellation-operation ownership across the unlocked I/O window so a competing prompt cannot begin between revalidation and the physical stop. Return/mark complete only after actual runtime absence or the synchronous exact stop reports success. Scheduling an async stop is not completion; if using the existing detached worker, it must carry intent ID and persist the final outcome/error itself with owner start/stop semantics.
5. If execution was replaced, only stop a still-existing old execution by captured ID if the runtime can verify it is the captured owned execution; leave replacement session state alone. If the same execution now hosts a different user turn/submission, do not stop that process. Mark this old intent `superseded` by its exact ID. This is the required successor preservation case, not a stop failure to retry against today's turn.
6. A typed confirmed missing runtime completes the intent; arbitrary lookup errors, blank IDs and unavailable recovery inventory keep it pending. On a restart, first finish standard authenticated native/durable runtime recovery; unavailable inventory is not absence. Continue per-row so one stop error does not suppress siblings.
7. For a reserved-only pre-session target, this packet adds the reservation cancellation fence to `LaunchErrandSession` and its initial-launch admission callbacks before creation, registration and first dispatch; Task 13 later reuses that fence for adoption. Seed durable reservation rows in the existing direct-launch test fixture instead of adding a test-only bypass for a missing row. A launch already past that boundary can bind this same initial `(session,turn,submission)` target to its exact execution, never to a later user turn. `recordLaunched` cannot resurrect a cancelled lifecycle; it asks the same teardown recovery seam to finish that initial execution.
8. `CancelAll`, `cascade`, and recovery independently include `intent.state=pending` rows even when projected status is cancelled. Iterate raw task/parent rows and check the intent before calling `Project`; a projection failure must not hide the pending obligation or abort all other rows. Project only to decide a new live-row cancellation, and collect row-specific errors with `errors.Join`. New cancellation counting still includes only newly cancelled live errands. Existing settled/cancelled rows with no pending intent remain no-ops. Batch delivery runs once per affected parent after durable cancellation decisions; stop retry does not redeliver notices.
9. Run bounded pending-intent retry on startup and existing ceiling/lifecycle sweep, including flag off. Do not rely on a second parent event or next backend boot. Cascade worker failure remains logged but durable intent is the authoritative retry queue.
