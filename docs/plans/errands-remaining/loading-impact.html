Proposed follow-up · 12 November 2026

Errands: load history on demand

Load the parent conversation with ordinary sessions and a small live overview. Fetch finished history when it is opened, and child details when that child is opened.

An impact map of the proposed change. Not an implemented fix or a finalized API design.

Why change it?

Historical Errands currently travel through normal session loading, boot enrichment and frontend reconciliation. Saved layout restoration can also create child panels before later filtering removes them.

One captured parent: 3 ordinary sessions ≈ 7.2 KB; 107 Errands ≈ 243 KB. Errands account for roughly 97% of its session-list body.

This measures payload contribution, not a proven speedup or memory leak. The capture did not show HTTP transcript requests for every historical child.

Three moments, three amounts of data

1 · Open the task

Parent + live overview

Ordinary sessions, running/queued/attention summaries, and authoritative counts and result indicators.

2 · Expand history

One page of finished rows

Fetch summary rows on demand. Load the next page only when requested.

3 · Open a child

That conversation

Load its session detail, transcript and needed subscriptions. Direct links use the same targeted path.

What changes across the codebase

01

Database reads

Read only the rows the screen needs.

Add compact live-summary reads and bounded history-page queries. Filter and paginate before loading full rows or joining child sessions. Consider indexes only after measuring the queries.

Impact: Less data read and materialized per navigation. Retained conversations and result records stay intact.

02

Service & status

Keep complete server authority behind a smaller read model.

Project running, queued and attention summaries in batches. Compute counts and pending-result indicators independently of the history page. A finished child can still have an undelivered result.

Impact: Counts, capacity and Stop-all stay correct even when most history has never been loaded.

03

Boot, HTTP & WebSocket

Separate ordinary navigation, history pages and direct child reads.

Keep historical children out of normal session-list and boot enrichment. Return explicit page/cursor information for history. Resolve direct child URLs without listing every sibling. Reconnect must restore live state without fetching all history.

Impact: Smaller initial responses and fewer enriched objects. Authorization and child/parent ownership still apply to every request.

04

Frontend data & cache

Represent a partial list as a partial list.

Keep live summaries, loaded history pages and opened-child detail separate. Update shared types and read clients together. Bound cached pages and details. Coalesce reads and reject stale responses. WebSocket updates must refresh counts and affected pages without rebuilding an unlimited history cache; completion and reactivation must not duplicate rows.

Impact: Normal session reconciliation stops processing the entire history. Unloaded history is not mistaken for an empty or deleted history.

05

Layout & child navigation

Avoid creating historical child panels in the first place.

Filter normal and maximized saved layouts before panels mount. Unknown identity must not fall back to an ordinary child tab while details load. Load an explicitly opened child and its required subscriptions on demand. Preserve ordinary tabs and Back navigation.

Impact: Prevents the temporary Errand-tab flash and avoids unnecessary panel work. A direct child link still works.

06

Desktop & phone UI

Fetch history when the user opens it.

Keep live activity immediately visible. Fetch the first finished-history page on expansion, then load more on demand. Add localized loading, empty and retry states. Retain the desktop popover and phone drawer, scroll region, touch targets and Back behavior.

Impact: The parent stays usable as history grows. Individual Stop, task-wide Stop-all and exact counts do not depend on fetched pages.

Results & execution

Preserve the existing delivery and runtime contracts.

Render saved result cards, including elapsed time, from their immutable metadata. Keep complete internal membership for delivery, cancellation and recovery. Do not silently paginate the agent-facing MCP list/await behavior.

Impact: No replay, lost result, or changed execution authority. Runtime cleanup remains separate from reducing browser history overhead.

Keep these boundaries intact

  • Ordinary sessions stay unchanged: this work does not make normal sessions lazy-loaded. Existing page loads, tabs, direct links, layout restoration, reload, reconnect and task switching must pass regression checks on tasks with no Errands and on mixed tasks.
  • No deletion: retained sessions and transcripts remain available.
  • No authority changes: capacity, pending results, recovery attention, Stop-all and flag-off inspection stay correct even with unloaded history. Never turn existing complete internal lists into partial pages.
  • No provider or shell rewrite: ACP, agentctl, executors, CLI and Tauri need no required behavior change identified so far. The desktop app inherits the shared web changes.
  • Separate work: runtime cleanup is already implemented. Asset compression, bundle splitting and the missing-result-delivery incident are outside this proposal.

Build and prove it in this order

  1. Define the read contract. Set task/parent history scope, stable cursor ordering, page size, summary fields and cache/invalidation rules. Decide whether to extend the browser list contract or add a dedicated one; update requirements, design and work order.
  2. Connect the complete path. Add bounded queries and boot reads, then typed clients/stores, layout filtering and desktop/phone history controls. Preserve existing agent-facing and internal consumers.
  3. Measure comparable tasks. Test zero, 100 and a larger finished history with the same build, ordinary sessions, network and cache conditions. Record response bytes, requests, reconciliation work, panel mounts, time to usable conversation and retained memory/subscriptions.
  4. Exercise real navigation. Assert zero history requests before expansion and bounded pages afterward. Test reload, switching, retry, direct links, late responses, reactivation, counters, Stop, saved cards and no temporary child tabs on desktop and phone.

Success: ordinary navigation no longer loads or reconciles every finished child. Visible history and opened conversations still behave correctly. Set timing and memory tolerances from the baseline, then report the measured improvement.
