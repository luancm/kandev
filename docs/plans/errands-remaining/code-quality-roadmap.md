Redesign must address a demonstrated maintenance problem, with fewer obligations spread across callers and a clear account of what becomes simpler.

## Redesign constraints and freedom

Start from the accepted [Errands decision](../../decisions/2026-10-23-errands-first-class-delegation.md), [delivery uncertainty decision](../../decisions/2026-10-30-errand-await-delivery-uncertainty.md), [recovery authority decision](../../decisions/2026-11-09-errand-recovery-settlement-authority.md) and current [history-loading design](../../specs/tasks/system-design/errand-history-loading.md). Avoid layering another coordinator or generic framework over existing ownership. Prefer a module with a small interface that owns its implementation details; moving the same bookkeeping into callers is not simplification.

Existing architectural choices can be challenged when evidence shows a disproportionate cost. A proposal that changes user-visible guarantees, compatibility or scope must state that tradeoff explicitly and return as a design decision before implementation. A behavior-preserving refactor must not silently guess missing identity, replay uncertain results, convert unknown work to success, or treat a terminal session label as proof of physical runtime absence. Preserve startup availability and isolation of ordinary-session behavior.

Separate low-risk removals from ownership redesign and persistence changes. Do not mix wholesale file moves, renaming and behavioral changes into an unreviewable patch. A temporary dual path needs a specific supported consumer or migration need and must disappear with that need; do not create a new permanent compatibility layer for an unshipped internal interface.

## Tests, documentation and comments

The user confirmed that the work so far is valuable as discovery of the feature's behavior and as executable functional and non-functional specifications. Preserve those assets while making the implementation replaceable. Before each refactor, map the relevant behavioral promises and measured limits to existing tests, identify meaningful gaps, and add missing regression coverage first. Reuse retained failure evidence where it already demonstrates that a test detects the intended defect.

Make black-box contract tests the primary safety net. Exercise the same stable interfaces as callers, asserting observable results, side effects and resource behavior. These can be API, service or module tests as well as browser tests; moving every check into slow end-to-end scenarios would reduce diagnostic value. Use real local persistence for transactional guarantees and controlled provider/transport boundaries for reproducible failures. Avoid coupling assertions to private helpers, internal call order or the arrangement of implementation structs. An externally required ordering, such as persisting a result before releasing its runtime, remains part of the contract.

Functional coverage includes result delivery, cancellation, retained conversations, restart/uncertainty and unchanged ordinary-session behavior. Non-functional coverage includes the established latency, memory, request/materialization bounds and runtime/subscription release checks. Preserve workloads, assertions and performance limits across an implementation-only refactor. Any justified contract or benchmark change must be explicit and assessed separately; do not weaken the oracle to fit the replacement implementation. Passing tests provides evidence for the scenarios and environments exercised, not a guarantee against every possible regression.

Keep targeted concurrency and crash-window tests when black-box end-to-end checks cannot reliably exercise those failures. Their internal scheduling or fault-injection setup may change with the design, while the safety assertions stay meaningful. Consolidate identical setup and redundant assertions; remove tests tied to deleted implementation details only after retained contract coverage protects the relevant failure. Avoid accumulating a second suite that merely mirrors each new helper.

Requirements describe behavior, system designs describe current ownership, ADRs preserve decisions, public docs explain usage, and the task plan describes current work. Correct stale prose/statuses and remove duplicated instructions. Consolidate completed execution chatter and repeated handoffs into a short evidence index where useful; verify links and the durable evidence location before removing files. Git history can retain superseded working notes, but irreplaceable evidence must not survive only in an ephemeral `/tmp` path. Preserve benchmark failures and exceptions rather than cleaning them out of the story.

Production comments should explain non-obvious invariants, ordering and compatibility. Remove obsolete migration notes and review-round narration after checking that they are obsolete. Do not delete a precise safety explanation just to reduce comment volume, or copy long implementation history into a replacement comment.

## Acceptance and relation to the pilot

For each selected slice, retain focused evidence for the flows it changes. Settlement/cleanup changes need completion, cancellation, restart and successor cases; persistence changes need the actual SQLite/PostgreSQL operations and upgrades; navigation/state changes need stale-response and ordinary-session controls plus relevant desktop/phone behavior. Run heavy checks sequentially with the existing build lock and retain process handles. Reuse unchanged verification receipts instead of repeatedly rerunning the whole feature; each concrete change or finding determines what must rerun.

Performance remains a first-delivery constraint. Preserve the [recorded baseline and exceptions](../errand-history-loading/summary-followup-handoff.md). Remeasure ordinary load/switching and zero/100/1000-history controls when affected paths change; compare the final candidate with matching upstream main. Report fixed feature cost separately from history growth, with no silent threshold relaxation. Test-only cleanup should not trigger an unrelated performance campaign.

The [bounded-use pilot](bounded-use-roadmap.md) tests everyday reliability; this roadmap tests maintainability and design cost. They inform each other. A small pilot may proceed on the verified deployed build while the audit is read-only. Do not introduce uncontrolled source changes during a measurement cohort, or widen autonomous routing before both the relevant design risks and observed pilot failures are resolved.

Completion means fewer responsibilities and coordination rules for maintainers to carry, removal of justified dead paths, clear current documentation and preserved behavior/performance. One scoped review of each frozen change, followed by rechecking concrete findings, is sufficient. Keep deferred improvements visible; do not turn this into an endless review of every file before anyone can use the feature.
