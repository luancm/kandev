## Findings and limits

`apps/web/components/task/dockview-layout-restore.ts` sanitizes saved panels for component validity and known foreign-environment session IDs, then calls `api.fromJSON`. It does not exclude Errand session identities. Its session context also includes all session IDs. `dockview-session-tabs.ts` subsequently filters Errands in `resolveAutoTabSessionIds` and reconciles tabs after session metadata is available. This is a concrete restoration gap consistent with the reported flash. Both files are unchanged relative to the live commit. Saved browser layout contents were not captured, so the exact offending layout is not yet reproduced.

`dockview-panel-content.tsx` passes panel visibility into `detailActive`, and `use-session-prompts.ts` gates subscription and fetch effects on that value. There is no basis yet to claim that all briefly restored tabs fetch transcripts. Panel creation/layout/subscription overhead still needs measurement.

Successful-completion runtime cleanup remains unimplemented in the current delivery package. The ten ready, successful Errand records are consistent with that gap. Cleanup is necessary independently of tab restoration; hiding tabs cannot release runtime resources.

## Scope correction: isolate the Errands regression

The user clarified that these loading problems appeared after adding Errands and wants investigation of that implementation's impact, rather than general Kandev optimization. Compression, bundle splitting and unrelated MCP metadata changes are outside this investigation. The HAR has no pre-Errands control and cannot establish that shared asset delivery explains the regression.

Splitting the actual captured session lists by immutable role establishes a direct contribution. The parent response contains three ordinary sessions whose compact JSON array is 7,218 bytes, plus 107 Errands whose array is 242,958 bytes. Approximately 97% of the 250,200-byte session-list body is Errand rows. The subtask has one ordinary row at 2,234 bytes and 32 Errand rows at 73,463 bytes, again approximately 97% of its 75,720-byte response. These are within-capture payload comparisons, not before/after loading-time benchmarks.

The boot entity graph separately includes 240,922 bytes of Errand session entities and 19,511 bytes of Errand model entries, plus per-session IDs and environment/worktree references. Thus historical Errands participate in normal task boot even while none is opened. `addTaskDetailSessionsState` in `apps/backend/internal/backendapp/boot_state_task_detail.go` iterates all session summaries, enriches their projections and builds session/model/environment/worktree maps. This is retained-history workload, not only active-worker workload.

`setTaskSessionsForTask` in `apps/web/lib/state/slices/session/session-slice.ts` merges every row on every list refresh and runs per-session reconciliation, including MCP history, environment mappings, prepare progress and idle-turn reconciliation. The capture's changing pending-action revisions affect all 110 rows. The ordinary-session path therefore processes 110 rows instead of the three ordinary rows; this is a count of processed rows, not a claim that rendering or latency is 37 times slower. The repeated requests amplify that cost, but their exact triggers remain unproven.

The saved-layout restore gap remains the strongest source-level explanation for transient Errand tabs. Creating and then removing historical child panels would add UI work independently of transcript fetching. HAR cannot determine whether their React content mounts before removal or how much CPU that costs, so absence of HTTP transcript fan-out does not rule out Errands-related UI overhead.

The next diagnostic packet should compare the same isolated ordinary task/session structure with zero versus 100+ retained completed Errands, keeping build, assets and network conditions fixed. Measure boot/list payload, session-list read count, reconciliation count/time, restored panel creation/removal and time to a usable parent conversation. Include both reload and warm switching. Identify refresh callers before altering retries or revision guards. The likely repair boundary is ordinary-session boot/navigation and layout restoration: historical child detail should be loaded through the parent-owned Errand path as needed, preserving explicit child URLs, live status, unread behavior and retained history. Validate the already implemented successful-runtime cleanup separately from retained-history UI cost. General asset optimization is not a prerequisite or acceptance condition for this regression.
