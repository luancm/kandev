# Errand await reception evidence

This specifies positive reception and uncertainty for [result delivery](../requirements/errand-result-delivery.md), extending the transactional [recovery and delivery design](errand-recovery-and-delivery.md). It follows the accepted [uncertainty decision](../../../decisions/2026-10-30-errand-await-delivery-uncertainty.md). [Repair Task 04](../../../plans/errands-review-repairs/task-04-await-outcome-recovery.md) owns implementation and regression evidence. No supported provider promises a complete negative reception oracle.

### Attempt states and response identity

States are `open`, `claimed`, `offered`, `uncertain`, `aborted` and `received`. `offered` is a sender-side authorization to hand the already assembled successful response to the MCP library, not evidence that the client received it. Commit it before the handler can return success; a failed or ambiguous offer commit makes the live handler choose its fenced error/abort branch. A normal live `offered` attempt is awaiting observation, not yet a user-facing recovery warning. A valid positive observation changes `offered` or `uncertain` to `received`. `received` and `aborted` are terminal decisions: a late abort cannot release a received attempt, and contradictory positive evidence for an aborted attempt is an invariant conflict to retain and diagnose, never permission to release or replay. An orphaned `open`/`claimed`/`offered` attempt without a proven abort or positive observation is conservatively `uncertain`. No timer, missing report, turn completion, socket outcome or process death changes uncertainty to `aborted`.

Extend the already planned attempt row with the immutable parent incarnation and harness generation captured from the authenticated MCP bridge execution when the attempt is created. They are host-owned attribution, never tool arguments or a read of whichever execution happens to be current later. Retain the first accepted receipt's stream ID, sequence, native tool-call ID, accepted payload hash/hash version and observation time on that attempt. Existing attempt items remain the immutable set of claimed `(errand_id, result_revision, captured parent_admission_generation)` identities. Attempts, items and their compact receipt identity survive event payload pruning until the existing task-deletion boundary; no full-response store is needed.

Add a bounded `await_delivery` object to the JSON body already returned as the successful MCP text result: `{ "version": 1, "token": T, "items": [{ "errand_id": E, "result_revision": R }] }`. The enclosing verified parent and native event owner provide task/session identity; the response object does not grant authority. Generate this object from the exact committed attempt snapshots used to assemble the response. Its item set is exactly the results actually carried by this response, with distinct IDs and at most five items; status-only and previously delivered rows do not acquire receipt items. A zero-item successful await can have an empty item list and cannot confer receipt on an errand result. Never derive revision identity from row CAS version, text, timestamps or a later reload. Keep duration, end reason, statuses, result content and existing returned-result markers unchanged. This object is correlation metadata, not itself a receiver acknowledgement. Put it in the existing JSON text body, not exclusively in MCP `_meta`, because supported native reports already preserve that body.

### Supported positive native observation

Implement positive extraction for two explicit source formats: the existing canonical Codex ACP MCP call/result path and the native Codex app-server `mcpToolCall` item completion. For Codex ACP, require the existing implementation-issued `is_mcp_tool_call` identity, tracked native tool-call ID and exact `kandev/await_errands_kandev` server/tool identity from `parseCodexMCPToolCall`, then the actual successful result from that same call's update. Inspect Codex's outer `{error,result}` envelope before unwrapping so a non-null error cannot be hidden by normalization. For native Codex, require `type=mcpToolCall`, `server=kandev`, `tool=await_errands_kandev`, a real item ID, actual successful `status`, no provider error and a non-null `result` containing the returned MCP body. Use the schema's `tool` field, not the generic emitter's current `toolName` fallback. Require the native source thread to be the owning parent thread; child-thread remapping or a nonempty parent-tool-call lineage cannot attest the parent's receipt.

Parse the complete successful MCP result's canonical JSON text body and validate the version, token and complete revision set before display preparation. Reject MCP error results, malformed or duplicate items, partial bodies, previews and contradictory metadata. Do not recursively search arbitrary output for a matching token. Require a supported native event actually carrying the result, not a remembered payload on a later status-only update. Attach a small serializable, adapter-issued `ErrandAwaitReceipt` observation to the existing normalized tool-update event, outside `Generic.Output` and `ToolCallContents`. It carries only token and exact items; the event supplies native call ID and stream ownership. The adapter is its sole producer; model/plugin content and synthetic status/callback paths cannot populate this field. Keep the current typed plugin ingress construction separate rather than trusting arbitrary incoming event JSON. Display preparation must retain this bounded observation without changing it even if it replaces the visible result with a preview. `NormalizedPayload.IsMCPTool()` is currently an internal, nonserialized bit: checking that bit after journal/JSON round-trip is not a receipt integration.

These two formats define the initial positive support boundary. Other ACP/native adapters, missing initial call provenance, history suppressed by session/load and older producers without the new identity may remain uncertain. Do not infer support from a display title or add a new recognizer without an actual programmatic identity/result fixture. In particular, no universal all-provider non-receipt guarantee is introduced, and no thread/read/private-history query is required by this repair.

### Trusted inbox decision, retries and recovery

Reduce the observation in the task repository's `ReceiveAgentDeliveryEvent` transaction, after the existing event-owner and sequence/hash validation and before committing the inbox event/received cursor. The repository compares the receipt with the authoritative attempt and its complete immutable item set, verifies the owning task, parent session, captured incarnation and harness generation, and records `received` plus the first evidence identity in the same SQL commit as acceptance of that native observation. Use host-authenticated `AgentDeliveryEvent` ownership, not task/session IDs copied from tool output. Do not relax the existing live-owner/generation fences to admit stale callbacks. The current errand row is not needed to establish historical receipt: a valid receipt can settle an old attempt even when its result has been replaced or superseded, without modifying the new revision, generation or token.

For a receipt-bearing event, take the task delivery guard before the existing session/stream write locks, then lock attempt/items and any affected errand rows in the established order. This must be coordinated with Task 03 and the other guard writers; do not acquire the guard late inside the already locked receive helper. Non-receipt events retain their existing path. The new transaction-local reducer belongs beside the attempt operations, called from `receiveAgentDeliveryEventTx` only after admission and identity validation. Operational SQL failure applying otherwise valid evidence rolls back both inbox acceptance and the attempt decision; no received/projected cursor or ACK can advance past it. An ambiguous commit is retried/read back by the same stream, sequence and content identity. Duplicate receipt events and repeated valid native reports are idempotent; retain the first evidence identity. Reuse accepted hashes and payload bytes, never rewrite replayed events to add a receipt.

Malformed, foreign, legacy or identity-mismatched observations cannot change attempt/result ownership; retain ordinary event evidence and diagnose a contradiction through existing diagnostics. A trusted positive observation that conflicts with a terminal abort is not silently reclassified as success or released. No receipt table or endpoint trusts arbitrary model, user, tool-title or transcript metadata. No service callback can declare `received` based solely on handler success.

Receipt reconciliation must run through normal authenticated journal replay/inbox ingestion after backend disconnection and restart, independently of the Errands release flag for retained attempts. A surviving agentctl's committed result observation is useful evidence and must resolve the corresponding unknown attempt when admitted. Put the decision in inbox acceptance, not the best-effort orchestrator tool-card callback: ordinary generic tools are not currently part of canonical atomic message projection, and duplicate/effect fast paths can skip callbacks. Since attempt receipt and inbox acceptance commit together, projection, journal ACK and backend payload retention cannot lose the only receipt between independent commits. Once committed, later event pruning or lifecycle/generation changes cannot revert `received`.

Keep the existing token-bound durable error/abort-intent retry path. The handler must irrevocably choose success or error once; a proven pre-success error branch may abort even after the sender-side offer was recorded, but no post-return transport callback can manufacture that proof. Offer/abort operations reject contradictory terminal decisions. “Retry” in this section means replaying the same receipt observation or abort intent, not issuing another await, returning cached result text, prompting the native client again or moving an uncertain claim back to pending. Backend SQL errors, lost ACKs and process replacement do not authorize result replay. Legacy delivered-await rows without the new identity remain uncertain.

### UI uncertainty timing and recovery

Expose a revision-bound, additive optional `delivery_state` on the existing errand projection with `received` and `uncertain` as its confirmed presentation values; omission means unavailable or still in progress, never proof of receipt. Keep `offered` internal. Do not announce uncertainty while an ordinary live await is waiting, claiming, handing off, or awaiting its native result update. A successfully reduced receipt clears any uncertainty for that exact attempt/revision and survives reload. Do not clear a newer revision's warning using an old attempt's receipt, and do not rewrite the historical successful response or child lifecycle status.

On loss/recovery of the owning invocation or stream, process available committed positive evidence before publishing the recovered classification. When an authenticated terminal for the originating turn has passed through ordered ingestion without a positive observation, the absence leaves delivery unconfirmed: report `uncertain`, not `aborted` or definitely undelivered. Store the originating turn/submission when the trusted bridge can capture it; if that association is unavailable, do not guess the latest turn for this UI transition, and use ownership-loss/recovery classification instead. A late valid native observation can still change `uncertain` to `received`. Providers that never report a usable result therefore get an honest recovery warning rather than automatic replay. Missing report, elapsed delay and terminal status establish no non-receipt and trigger no release.

Only a current result actually claimed by such an unresolved attempt gets “Result delivery uncertain”. Zero-item/status-only waits do not mark every named errand uncertain. Preserve the existing desktop panel and phone drawer, Open to the retained child transcript and existing composer for deliberate manual recovery. Do not add a resend action or a positive badge that claims model cognition. Existing “result returned” tool-card text means content carried in that historical response, not a durable native receipt. Update the shared uncertainty line from committed current evidence through existing errand.updated/list hydration; a missed publication is repaired by the existing reconnect/list path without child polling. All new copy follows existing locale rules.

## Compatibility and acceptance

| Source | Positive evidence | Missing or unsupported evidence |
| --- | --- | --- |
| Codex ACP | Tracked canonical MCP call and actual successful result with exact attempt/revisions | Retain unknown; do not infer from display labels, status-only updates or suppressed history |
| Codex app-server | Owning-thread successful `mcpToolCall` item with actual result and exact identity | Retain unknown; no history crawl or private database dependency |
| Other adapters and older producers | No positive recognizer is assumed | Conservatively uncertain after recovery/terminal classification; no automatic replay |
| Legacy claims without attempt identity | Cannot establish exact token/revision receipt | Retain unknown for explicit inspection/recovery |

Verification uses native-shaped fixtures, journal truncation/reopen/replay, authenticated SQL inbox transactions on SQLite/PostgreSQL, loss/duplicate/hash conflicts and terminal abort/receipt races. The real journal plus mocked provider boundary proves integration, not a live-provider crash guarantee. The work order owns exact regression names and commands. Backend admission failures never become permission to rerun the result.
